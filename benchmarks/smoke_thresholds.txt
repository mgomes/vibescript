# Benchmark smoke thresholds for CI guardrails.
# Format:
# <benchmark_name> <max_ns_per_op> <max_allocs_per_op> [max_bytes_per_op]
#
# Enforced by scripts/bench_smoke_check.sh, which CI runs on every pull
# request and push to master (the "Benchmark smoke gates" step in
# .github/workflows/benchmarks.yml). A breach fails the workflow.
#
# Keep thresholds intentionally loose enough to avoid platform flake,
# but tight enough to catch obvious regressions.
#
# ns/op caps stay wide: wall time is GC- and shared-runner-variance
# sensitive, and past tight ns caps tripped intermittently on unrelated
# PRs. Alloc and byte caps are the stable signals and are kept at
# roughly 1.5-2x the measured floor; they were re-based in July 2026
# after the boxed-mutator, call-boundary, and estimator-memo work
# lowered the floors far below the old caps, which had grown loose
# enough (up to 20x actual) to let a full regression of those wins
# pass CI unnoticed.

BenchmarkExecutionArithmeticLoop 5000000 30 6000
BenchmarkExecutionStepLoop 16000000 25 6000
# The ns cap sits well above the ~42ms this benchmark takes on the shared CI
# runner (about 3x a dev laptop): the old 40ms cap straddled the runner's floor
# and flaked. Its alloc and byte caps stay tight — those are the stable signals.
BenchmarkExecutionArrayPipeline 64000000 100 150000
# Iterating rows while summing into an outer local. The ns cap is what matters
# here: the accumulator's rebind used to invalidate the block-region memo every
# iteration, making the walk quadratic in the row count (~41ms at 600 rows
# versus ~0.85ms now), so a regression overshoots this cap by more than an order
# of magnitude even on a slow runner.
BenchmarkExecutionEachRowsScalarAccumulator 20000000 2800 800000
BenchmarkExecutionArrayPushAccumulation 3600000 900 120000
BenchmarkExecutionArrayConcatAccumulation 4200000 2400 150000
BenchmarkExecutionMethodDispatchLoop 8000000 1000 130000
BenchmarkBuiltinMemberDispatchLoop 5000000 50 8000
BenchmarkCallTypedCompositeValidation 14000000 1100 160000
BenchmarkExecutionCapabilityFindLoop 12000000 6500 700000
# Ruby-style hash insertion order stores one lookup-key slot per entry, a
# bounded per-hash cost these two benchmarks reflect in their floors
# (a workflow loop's per-iteration literals; JSON.parse of an object 80x).
BenchmarkExecutionCapabilityWorkflowLoop 16000000 13000 2000000
BenchmarkExecutionJSONParseLoop 3000000 2500 210000
BenchmarkExecutionJSONStringifyLoop 3000000 800 60000
BenchmarkExecutionRegexReplaceAllLoop 4000000 1200 30000
BenchmarkExecutionTallyLoop 12000000 1200 550000
BenchmarkCallShortScript 5000 12 3500
BenchmarkModuleRequireCacheHit 120000 60 10000
# Deep-recursion call path (naive fib(20), ~13.5k nested calls). The loop-shaped
# benchmarks never grow the env stack, so this is the only gate on call-setup
# allocation churn (argument slices, non-local-return signals) and, above all,
# the call-frame environment recycler: reuse-eligible frames are pooled and
# reused instead of allocated per call, so the alloc/byte floors sit near zero
# (a bounded free list plus the returned values) rather than one env per call.
# The caps are tight on purpose -- a regression that stopped recycling frames
# would restore ~22k allocs/op and must fail here. Runs under an unlimited memory
# quota, matching the CLI's default xhigh profile, so the estimator walk is out
# of the measurement. The paired BenchmarkExecutionRecursiveFibQuota
# (estimator-heavy, deliberately noisy) is left out of the smoke gate; it exists
# for profiling the memory-quota path.
BenchmarkExecutionRecursiveFib 30000000 200 40000
